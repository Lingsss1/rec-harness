MetaBalance

它回答的不是“哪个任务方向错了”，而是一个更朴素、也更工程的问题：哪个任务的梯度声音太大，正在淹没我们真正关心的目标？

一句话方法公式实验证据接入 Kai V2复现方案成本与边界Leader Q&A三篇对比

一句话讲给 Leader

现有 Base 已经用可学习 loss weight 平衡任务，但一个标量无法描述“不同训练阶段、不同共享模块”的动态失衡。MetaBalance 在每个共享模块上比较 CTCVR 与 CTR/PXR/PED 等任务的梯度范数，把辅助梯度温和拉向主任务量级；第一阶段我们只做只读诊断，先验证 Base 是否真的存在量级支配，再决定是否改训练。

它看什么每个任务对同一共享参数块的梯度 L2 范数。
能诊断什么辅助任务梯度过强，或弱到几乎不起作用；并定位发生在哪个模块。
不能诊断什么梯度方向是否冲突、某个神经元是否真正承载因果功能。

方法：比较“更新力度”，不是比较 loss 数值

设主任务损失为 L_tar，第 i 个辅助任务为 L_aux,i，对共享参数块 θ：

G_tar = ∇θ L_tar G_aux,i = ∇θ L_aux,i G_total = G_tar + Σᵢ G_aux,i

诊断量是 ||G||₂。如果辅助任务范数远大于主任务，它对共享表示的更新更强；如果远小于主任务，它可能几乎没有提供有效训练信号。

稳定测量：范数的指数滑动平均

m_tar(t) = β · m_tar(t−1) + (1−β) · ||G_tar(t)||₂ m_aux,i(t) = β · m_aux,i(t−1) + (1−β) · ||G_aux,i(t)||₂ 论文经验设置：β = 0.9

真正用于训练的缩放

G'aux,i = G_aux,i · w_aux,i w_aux,i = 1 + r · (m_tar / m_aux,i − 1) r = 0：不改；r = 1：辅助梯度范数完全对齐主任务；0<r<1：部分拉近

三种策略：A 只压低过强辅助任务；B 只放大过弱辅助任务；C 两边都调。论文用验证集选择策略与 r。对线上精排，建议先从 A 开始，因为“放大一个弱但噪声大的任务”风险更高。

直觉例子

假设 Share-bottom 上 CTCVR、CTR、PXR 的滑动范数分别为 0.2、2.0、0.05，取 r=0.5，则 CTR 权重为 0.55，PXR 权重为 2.5。注意：这里只改长度，不改方向。

论文证据：有效，但证据对应的是“单一主目标 + 辅助任务”

证据结果我们怎么解读
IJCAI-2015、UserBehavior-2017；购买为主任务，点击/加购/收藏为辅助相对最强基线，IJCAI-2015 NDCG@10 提升 8.34%；UserBehavior-2017 NDCG@10 提升 5.77%，论文对多数最优项做双侧显著性检验 p<0.05。场景与推荐多行为学习接近，可信度高于纯 CV 迁移。
消融 rr=0 不平衡；r=1 也非最优；示例中 r=0.7 最好。“范数相等”不是目标，必须用验证集选温和程度。
移动平均消融去掉移动平均，两个数据集都有下降，其中一个下降明显。不能用单个 batch 下结论；至少跨数百/数千步聚合。
与方向方法组合论文报告朴素叠加方向方法时多数性能下降。量级与方向诊断可并行，但优化动作不可默认叠加。

迁移到当前 Kai V2 Base

先定义谁是“主任务”

MetaBalance 强依赖单一主目标。若本轮目标是冷启动追平线上 CTCVR，则建议：

角色Kai V2 中的任务/损失备注
主任务cross_entropy / xentropy（CTCVR）与当前主排序目标一致时才这样设；若北极星是 GMV，应重选主任务。
核心辅助ctr_xentropy、pxr_xentropy、ped_xentropyCTR、PXR、播放完成等高频行为最可能量级较强。
扩展辅助CID、reco、global/direct pay、rocket、GMV、gen、interest、CL先不要一次全开；不同采样权重和稀疏 mask 会让解释复杂。

Hook 在哪里

  1. 第一优先：share_bottom_layer_new_0，即 13,175→1,024 的共享底座。所有主任务塔从这里分流，解释最干净。
  2. 第二优先：input_compress_token 与 hstu_raw_sequence 内的共享参数。代码对它们使用单独的 dense optimizer2，必须分开出报表。
  3. 暂缓：Sparse Embedding。PS 参数巨大、稀疏梯度范数受活跃 ID 数影响，需要按访问量归一化后才可比。
关键工程差异：当前 Base 已有 exp(-w_task) 可学习 loss weight。这并不等价于 MetaBalance：前者每个任务一个全局标量，后者对每个共享参数块、每个 step 动态缩放。第一项诊断正是验证现有权重是否仍留下模块级失衡。

最小复现：先诊断，后干预

1. 固定模型与数据
成熟 Base checkpoint + 同一份离线时间窗。
→
2. 拆任务梯度
每 20–100 step 对共享块分别求 task gradient。
→
3. 形成热力图
记录 log 范数、比例、EMA、训练阶段。
→
4. 可证伪判断
支配是否持续、是否与弱任务 AUC 停滞同现。
→
5. 小规模 A/B
只选一个共享块、策略 A、r∈{.2,.5,.7}。

建议验收标准

  • 诊断稳定性：换 batch/seed 后，主要支配关系一致；报告 P50/P90，而非单步最大值。
  • 因果验证：缩放前后主任务离线 AUC/GAUC 与关键辅助任务同时记录；不能只看梯度更“均衡”。
  • 成本归因：记录每 step wall time、显存、吞吐；与现有可学习 loss weight 做同预算对比。

工程成本与证据边界

项只读诊断完整训练改造
反向计算抽样 step 逐任务求梯度，可控制成本；推荐离线跑。必须获得每任务对共享块的独立梯度；名义复杂度同阶，但现实中通信、autograd 和多任务数会明显增时。
额外状态每任务×模块一个 EMA 标量，几乎可忽略。仍只需 EMA 标量；但需要缓存或流式合成各任务梯度。
改动范围训练图加 gradient tap，不改线上 serving。改 optimizer 前的梯度合成；推理图不变。
边界：论文不是 Kai、不是流式训练，也没有覆盖 HSTU、大量 Sparse PS、多目标商业约束。8.34% 是特定公开离线排序实验上的相对提升，不能外推为我们的预期收益。

汇报结论

MetaBalance 最适合当前项目的价值不是“直接上一个新优化器”，而是先提供一个低歧义问题：现有多任务 Base 中，哪些辅助任务正在什么共享模块上，以多大力度改写主任务表示？只有这个问题被数据证实后，才进入梯度缩放实验。
