# Amazon 拒绝角色进入优化器轨迹

方案 §5.5 要求优化器能检查失败与错误归因。Amazon 原先仅从 `role_completed` 生成决策轨迹，即使失败角色已归档，优化器也看不到拒绝原因。

现在 `collect_traces` 也读取截止点内具有 `archive` 的 `role_rejected`，核验提交输入、角色、拒绝原因与全部引用对象。轨迹保留调用前输入、源码、图版本，以及进程收据中的传输状态、时间和费用；缺失进程信息标为 unknown/空值，不由可重试标志推测执行成功。

拒绝轨迹标记 `role_admission: rejected`，`role_output` 为 null，原始响应与返回草稿只提供 CAS 引用。非法 JSON 因而不会被当作可用结构化决策，也不会阻止优化器读取失败记录。CLI 返回 success 与主机准入失败分别记录，不能混成同一个状态。

拒绝轨迹的 ID 包含拒绝事件 hash，并以 `role_call_id` 保留原调用身份；若同一调用后来被恢复接纳，两条事件不会覆盖彼此。轨迹条数不作为调用计数，费用审计仍以提交和预算账本为准。`optimizer_handoff.request` 排除所有被拒角色，不能拿“传输成功但角色合同失败”的记录建立测量缺口实验证据。

拒绝信息不插入调用前 `visible_state`。旧拒绝事件没有 archive 时不推断输入和草稿；新的失败记录只在其提交截止点之后可见。它们可用于诊断研究流程，不能说明模型或方法无效。

测试覆盖真实 `_role` 控制器路径上的模拟 crash 与成功传输后的非法响应、两次受限重试、拒绝信息与原始输入分离、前缀截止点、未来信息排除，以及测量转交资格过滤。32 项相关测试通过；本次未发起新的真实 Codex 调用或训练。

完整核心检查通过：公开边界、语法及 445 项测试（424 项通过、21 项环境条件跳过）。新增路径尚未打入 v17 安装包，也不回填历史真实任务的缺失档案。
