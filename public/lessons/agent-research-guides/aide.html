POSITIONING

一句话定位

把机器学习工程重写成“在代码空间里优化一个可执行解”的问题。它不维护一段无限增长的对话，而是维护解树：每个节点是一份脚本，每条边是一次 Draft、Debug 或 Improve。

先看结论

RecHarness 可直接借用“artifact-first”思想：每个 trial 必须对应 commit/config/log/metric，而不是只存聊天。把 Improve 约束为单一假设，可显著提高线上归因能力。

SYSTEM DESIGN

设计思想：它改变了哪一层？

  1. 搜索对象不是自然语言计划，而是可运行 Python 程序；执行结果直接成为下一轮决策证据。
  2. Improve 被限制为一次原子修改，使性能差异更容易归因。
  3. 选择策略优先高分有效节点，同时保留修复 buggy 节点的入口，避免搜索完全坍缩到单一路径。
01 State任务、workspace、预算与当前 artifact
02 Select选择分支、组件或阶段目标
03 Operate生成、修复、改进或组合代码
04 Evaluate执行并获得指标、错误与审阅信号
05 Remember写回持久状态并决定下一跳

MATHEMATICAL CORE

数学原理

v* = argmax(v ∈ V_t) F(v) child = f_operator(parent, Σ(T)) Σ(T) = compress({score, hyperparameter, traceback}_history)

AIDE 是黑盒、梯度自由的程序优化。F(v) 可取交叉验证分数；策略用当前观测到的最高 fitness 做贪心利用。由于 LLM 变换无法微分，搜索质量取决于代码算子是否产生局部、可测量的邻域。

阅读提醒：这些 Agent 多数不是在参数空间求可微最优，而是在 artifact/code space 做黑盒搜索。公式描述的是算力如何在候选之间分配，而不是替代真实实验。

MEMORY ARCHITECTURE

Memory 不是聊天记录

Write · 写什么每次执行后写入代码、验证指标、运行状态、traceback 与关键超参。
Read · 谁在何时读Σ(T) 只抽取分数、超参和调试线索，注入 Draft/Improve 提示；节点本身保持自包含。
Forget · 如何控噪不是删除原始节点，而是通过摘要压缩控制 prompt；代价是跨分支的结构性经验可能丢失。

建议的数据结构

SolutionNode { code, parent_id, operator, status: valid | buggy, validation_score, runtime, traceback } PromptMemory = summarize(solution_tree)

实现时应把 raw artifact 与 prompt view 分离：前者完整可追溯，后者按 operator/阶段动态裁剪。摘要只是读取视图，不应覆盖原始实验记录。

不能从论文直接推出什么

  • 贪心选择容易围绕局部最优反复打磨。
  • 全局摘要会混入与当前分支无关的信息，也可能造成模式坍缩。
  • fitness 依赖验证集，若验证设计不稳，树搜索只会更快地过拟合代理指标。

DESIGN TRANSFER

最小复现顺序

  1. 先定义 artifact schema 与可重复的 evaluator。
  2. 只实现一种 operator 和一种 selection policy，得到可运行 baseline。
  3. 加入按作用域读取的 memory view，并记录重复试验率。
  4. 最后再增加并行、Crossover、Reviewer 或多角色，逐项做消融。
