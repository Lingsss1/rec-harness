POSITIONING

一句话定位

MLE-STAR 不从空白内部知识开始，而是先从 Web 检索任务适配模型，再用消融定位最值得改的代码块。外循环选组件，内循环只深挖该组件，解决“每轮都重写全管线”的粗粒度探索问题。

先看结论

非常适合模型内部诊断后的闭环：AXG/Shuffle 先提出模块，targeted refinement 只在该模块内生成候选；每轮保留 block-level memory，形成可审计的局部优化轨迹。

SYSTEM DESIGN

设计思想：它改变了哪一层？

  1. 先检索并实现多个 task-specific model，按验证分数排序后合并成初始解。
  2. 用自动消融估计每个代码块的边际贡献，选择最关键组件作为下一轮目标。
  3. 内循环并行提出多个策略，只编辑目标块；历史消融摘要和 plan-score 轨迹用来驱动多样化。
01 State任务、workspace、预算与当前 artifact
02 Select选择分支、组件或阶段目标
03 Operate生成、修复、改进或组合代码
04 Evaluate执行并获得指标、错误与审阅信号
05 Remember写回持久状态并决定下一跳

MATHEMATICAL CORE

数学原理

T_abl^t = Summarize(a_t, Execute(a_t)) block_t = argmax_b | h(s_t) - h(Ablate(s_t, b)) | s_{t+1} = ReplaceBlock(s_t, block_t, best(plan_1…plan_k))

核心近似是组件级 leave-one-component-out 归因。若移除或替换块 b 导致性能大幅下降，则把它当作高杠杆点。它不是严格 Shapley value：组件之间有交互时，单块边际效应会依赖当前代码上下文。

阅读提醒：这些 Agent 多数不是在参数空间求可微最优，而是在 artifact/code space 做黑盒搜索。公式描述的是算力如何在候选之间分配，而不是替代真实实验。

MEMORY ARCHITECTURE

Memory 不是聊天记录

Write · 写什么保存检索候选、每轮消融脚本/结果摘要、已修改组件集合，以及 plan→code→score 轨迹。
Read · 谁在何时读外循环读取历史消融摘要以减少重复选块；内循环读取同一组件的历史尝试作为反思反馈。
Forget · 如何控噪原始网页与完整执行日志不持续塞入上下文，只保留候选来源和结构化摘要。

建议的数据结构

RefinementMemory { retrieved_models[], ablation_history[{block, delta, summary}], block_trials[{block, plan, score, artifact}], modified_blocks[] }

实现时应把 raw artifact 与 prompt view 分离：前者完整可追溯，后者按 operator/阶段动态裁剪。摘要只是读取视图，不应覆盖原始实验记录。

不能从论文直接推出什么

  • Web 检索会引入可用性、数据污染和复现风险。
  • 消融代理可能误判强交互模块，且自动生成的消融脚本本身可能不公平。
  • 只优化局部块有利于归因，但可能错过需要跨组件协同的大改。

最小复现顺序

  1. 先定义 artifact schema 与可重复的 evaluator。
  2. 只实现一种 operator 和一种 selection policy，得到可运行 baseline。
  3. 加入按作用域读取的 memory view，并记录重复试验率。
  4. 最后再增加并行、Crossover、Reviewer 或多角色，逐项做消融。
