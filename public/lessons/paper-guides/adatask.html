AdaTask

单步梯度范数只能告诉我们“现在谁声音大”；AdaTask 追踪的是参数长期究竟被谁推动，并进一步把 Adam/Adagrad 的历史状态按任务拆开。

一句话诊断量优化器证据接入 Base复现成本边界Leader Q&A三篇对比

一句话讲给 Leader

当前 Base 使用 AdagradW 且多任务共享 13,175→1,024 的底座。即使每个 batch 的 loss weight 看起来合理，Adagrad 的历史平方梯度仍可能长期被 CTR 等高频任务占据，使稀疏的 CTCVR 实际步长被压小。AdaTask 提供 rAU 指标确认这种“长期更新支配”，并用按任务拆分的优化器状态修复。

它看什么每个任务对每个共享参数造成的平方更新 EMA 及占比。
能诊断什么谁长期主导共享层、被支配任务是否因此拿到过小有效学习率。
核心区别MetaBalance 看当下梯度量级；AdaTask 看经优化器后的长期更新历史。

诊断量：Average of squared Updates（AU）

对共享参数 θᵢ、任务 k、训练步 t，先得到该任务导致的参数更新 Δθᵏₜ,ᵢ：

AU(i,t,k) = γ · AU(i,t−1,k) + (1−γ) · [Δθᵏ(t,i)]² rAU(i,t,k) = AU(i,t,k) / Σₖ' AU(i,t,k')

rAU=0.8 的含义不是“这个参数对任务 k 有 80% 的业务价值”，而是按该定义的近期累计平方更新中，80% 来自任务 k。两任务时，长期接近 0.5 才表示更新量级较均衡。

为什么看 update，而不只看 gradient？

Adagrad / RMSProp 的示意更新： Δθᵏ(t,i) = − η · gᵏ(t,i) / (sqrt(G(t,i)) + ε)

同样的梯度在不同历史累积量 G 下，会得到不同实际步长。rAU 因而比原始梯度更接近“任务真正改了多少参数”。论文还用加噪实验验证：扰动高 rAU 参数，对相应任务伤害更大；但这仍是实验关联证据，不是严格因果归因。

方法：把优化器记忆按任务拆开

普通多任务 Adam/Adagrad 先把任务梯度合在一起，再维护一套历史状态；大梯度任务会改变所有任务共享的分母与动量。

普通：G(t,i) = γG(t−1,i) + (1−γ)[Σₖ gᵏ(t,i)]² AdaTask：Gᵏ(t,i) = γGᵏ(t−1,i) + (1−γ)[gᵏ(t,i)]² mᵏ(t,i) = βmᵏ(t−1,i) + (1−β)gᵏ(t,i) θ(t+1,i) = θ(t,i) − Σₖ η · m̂ᵏ(t,i)/(sqrt(Ĝᵏ(t,i))+ε)

这不是简单地“调 loss 权重”。它让同一个共享参数对每个任务有独立的历史平方梯度/动量，因此 CTR 的大梯度不会直接把 CTCVR 的自适应学习率分母撑大。

轻量版 LAdaTask

完整版本需要为每个任务维护参数级状态。论文提出按层/模块聚合：同一层的参数共享任务贡献系数，以减少状态量。代价更低，但实验收益也弱于完整 AdaTask。

论文证据：有推荐数据，但收益与任务取舍要讲清

数据/实验关键结果边界
TikTok 两任务被支配任务 A AUC 相比 EqualWeight +1.51%，平均 AUC +0.61%，加权 AUC +0.99%；主导任务 B 相比 EqualWeight −0.51%。改善弱任务可能牺牲强任务，并非所有任务一起涨。
WeChat 四任务平均 AUC 0.9359，为表中最好；加权 AUC 0.9311，低于 CAGrad 0.9336。若业务权重偏向原主导任务，AdaTask 未必是最优商业解。
CityScapes相对 EqualWeight，弱任务两项 error 改善 15.78%/21.59%；整体 Δp=9.34%。CV 不是推荐，主要用于验证机制泛化。
rAU 诊断CityScapes 中 EqualWeight/GradNorm 有 99%/95% 共享参数被任务 B 支配；AdaTask 后 93% 落入平衡区。“平衡”按作者 rAU 分箱定义，不等价于业务最优。

当前 Kai V2 的具体 Hook

为什么这个 Base 特别值得先测 AdaTask

  • Dense 与 Sparse 都使用 kai.optimizer.AdagradW，历史平方梯度直接决定有效学习率。
  • Dense 参数被拆成普通部分（lr=1.0）与 HSTU 相关部分（lr=0.3）：input_compress_token、hstu_raw_sequence。两组必须分别计算 rAU。
  • 训练 loss 包含 CTCVR、CTR、PXR、PED、CID、Reco、Global/Direct Pay、Rocket、GMV，以及 gen/interest/CL；标签频率、sample weight 与 mask 差异很大，具备长期支配的条件。
诊断单元任务映射先看什么
share_bottom_layer_new_0CTCVR / CTR / PXR / PED模块级 rAU 分布、各任务有效学习率比；先不把十余个 loss 全塞进来。
HSTU 两个 scope同上HSTU 独立 optimizer 是否让支配关系与 Share-bottom 不同。
Sparse Embedding高频/低频标签任务第二阶段；按活跃 ID 和非零梯度坐标归一化，否则高覆盖任务天然占优。

主任务不必先指定。AdaTask 的诊断阶段可以同时计算所有任务的 rAU，先发现谁支配谁；但是否“修复”为均衡，必须由线上主指标和任务优先级决定。

复现方案：三层递进，避免一次改 optimizer

A. rAU 仪表盘
保持现有训练，只记录各任务模块级梯度与模拟 update。
→
B. 验证机制
比较 rAU 支配、有效 lr、各任务 AUC 学习速度。
→
C. LAdaTask
只对 Share-bottom，按模块共享状态。
→
D. 完整 AdaTask
仅在弱任务收益和成本都过线时推进。

离线第一版输出

  1. 横轴训练 step，纵轴模块；每个格显示 dominant task 与 rAU。
  2. 对 CTCVR/CTR/PXR/PED 输出有效学习率 P50/P90，以及梯度为零的比例。
  3. 对照任务 AUC 学习曲线：若 CTCVR rAU 很低且学习明显慢，才形成可信假设。
  4. 用固定数据、固定初始化对比现有权重、LAdaTask、完整 AdaTask；至少 3 seeds。

工程成本与证据边界

版本状态/计算适合当前阶段
只读 rAU 诊断每任务梯度 + 每任务×模块统计；抽样 step 可降成本。最适合，先确认问题存在。
完整 AdaTaskK 个任务需要 K 套优化器状态；相对普通版本多 K−1 份中间状态。论文称单次反向可实现，但框架是否支持逐任务偏导需要实测。高成本，尤其 PS Sparse 与多 optimizer 架构。
LAdaTask模块级任务贡献状态，显存小；收益弱于完整版本。最合理的首个干预版本。
证据边界：论文没有验证流式训练、Kai AdagradW、超大 Sparse PS 与十余任务。作者明确承认：提升被支配任务可能损害主导任务，且没有给出一般非凸收敛证明。

汇报结论

AdaTask 对当前 Base 最有价值的切入点，是把“多任务 loss 权重问题”升级为优化器历史状态是否被高频任务长期占领。先用 rAU 做证据，再决定是否值得承担任务级 optimizer state 的工程成本。
